# 022. Реализовать Worker consumer массовой операции

**Этап:** 5. Выполнение, повтор и восстановление

## Цель

Безопасно обработать каждую задачу независимо с соблюдением rate limit и конфликт-контроля.

## Контекст продукта

Непосредственно перед записью задача перечитывается; изменившаяся задача получает `Конфликт`.

## Объём

- Обрабатывать задачи операции по устойчивой очереди.
- Сверять контрольную версию и повторно проверять необходимые права.
- Применять изменения от имени текущего пользователя через adapter.
- Сохранять результат, предыдущие значения и версию после изменения по каждой задаче.
- Классифицировать временные и постоянные ошибки и соблюдать API rate limits.
- Проверять номер попытки запуска из Queue-сообщения до старта и игнорировать устаревшие сообщения.
- При неопределённом результате сначала перечитывать задачу; слепой повтор `tasks.task.update` запрещён.

## Вне объёма

UI прогресса, отчёты и ручной повторный прогон.

## Требования

- Ошибка одной задачи не останавливает остальные.
- Повторная доставка сообщения не изменяет уже окончательно обработанную задачу повторно.
- Повторная доставка точного результата не меняет счётчики; отличающийся результат фиксируется как системный конфликт.

## Критерии приёмки

- Конфликтная задача не перезаписывается и получает статус `Конфликт`.
- Каждый успешный и неуспешный результат сохраняется отдельно.
- Временный rate limit приводит к контролируемому retry без потери задач.
- Повторная доставка подтверждена тестом идемпотентности.

## Зависимости

004, 008, 018, 021.

## Реализация

Consumer расшифровывает приватный план, проверяет попытку, права и состояние каждой задачи, затем
записывает результат через SQL claim и fenced mock CAS. Предыдущие значения шифруются в Supabase;
неопределённый ответ перечитывается без слепого повтора записи. Queue continuation, cron redrive,
rate limit, отдельные результаты и аудит покрыты Worker и SQL тестами. Тестовый mock хранит
состояние задач между экземплярами API и consumer. Реальный Bitrix-портал отсутствует, поэтому
его интеграция не проверялась. Независимые ревью: 9/10 и 8/10; последнее замечание по producer
binding consumer исправлено.

Проверки не выполнялись; пользователь запускает `bun run check` и `bun run db:docker:test`.
