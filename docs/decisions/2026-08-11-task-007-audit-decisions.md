# Решения реализации: задача 007

Дата: 2026-08-11  
Статус: утверждено  
Текущая задача: **007. Реализовать неизменяемый журнал событий аудита**.

Источник: `tasks/007-append-only-audit.md`.

## Граница задачи

Задача создаёт контракты, append-only writer, ограничения базы, безопасное чтение и
подготовленную функцию retention. Она не создаёт UI, HTTP mutation API, планировщик
очистки или вызовы аудита из будущих пользовательских сценариев.

## Зафиксированные правила

1. Инициатором может быть пользователь или система; системные действия не
   приписываются сотруднику.
2. Аудитируются успешные действия, значимые ошибки и подтверждённые отказы в правах.
   Ошибки формы, прогресс, результаты отдельных задач и технические дубли не попадают
   в журнал.
3. Событие имеет один обязательный основной объект и до восьми типизированных связей.
4. Технический повтор подавляется по внутреннему event key; новый осознанный повтор
   создаёт новое событие.
5. Неопределённый результат внешнего действия имеет outcome `uncertain`; после
   сверки добавляется отдельное итоговое событие.
6. Детали события строятся по allowlist-схеме. Токены, webhook, raw HTTP, содержимое
   задач и защищённые предыдущие значения запрещены.
7. Обновление аудит-событий запрещено всегда. Удаление возможно только через
   ограниченную функцию для записей старше двух лет; scheduler относится к задаче 031.
8. Хранятся `occurredAt` и `recordedAt`; интерфейс позднее покажет время портала.
9. Имя пользователя и название объекта сохраняются на момент события. Текущий статус
   и доступ к живому объекту проверяются отдельно.
10. Correlation ID — безопасный код Task Commander. Внутренние ID очереди, базы и
    дедупликации не отображаются.
11. Массовая операция аудитируется по жизненному циклу и агрегатам, без событий на
    каждую задачу. Частичный результат использует `partial`.
12. Скачивание означает предоставление доступа к файлу, а не доказанное сохранение на
    устройстве пользователя.
13. Изменения доступа сохраняют только фактически применённую разницу прав и полей.
14. Writer строг при записи и tolerant при чтении неизвестных будущих action-кодов.
15. При недоступности аудита новые значимые действия не начинаются. В Worker запись
    аудита ожидается синхронно, а не выполняется background best-effort работой.
16. Первая значимая временная ошибка и окончательный исход аудитируются; повторные
    внутренние попытки остаются в эксплуатационной телеметрии.
17. Успешный просмотр журнала не аудитируется. Подтверждённый отказ без `view_audit`
    записывается как `denied`; неидентифицированные запросы остаются в security telemetry.
18. Пустые повторные команды не создают событие. Завершённый бизнес-процесс с нулевым
    количеством изменений создаёт успешное событие с агрегатами.

## Техническая модель

- Контракт определяет нейтральный action-каталог, outcomes
  `success | partial | failure | denied | uncertain`, actor, основной объект, связи и
  action-specific details.
- `append_audit_event` выполняет insert, формирует sha-256 event key из стабильного
  scope/action/slot и возвращает прежнюю строку при идентичной повторной доставке.
- Прямые `INSERT`, `UPDATE` и `DELETE` для runtime service-role закрыты. Для чтения
  остаётся `SELECT`, для записи — только RPC.
- Writer очищает запрещённые ключи и известные токеновые/URL-паттерны до строгой
  валидации. Raw внешние ошибки не являются допустимым полем контракта.
- Будущие атомарные RPC задач 008 и 021 вызывают SQL helper в той же транзакции.
