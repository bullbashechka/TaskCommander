# Решения задачи 021: создание и запуск операции

- Подтверждённый preflight расходуется только в SQL транзакции, которая блокирует владельца и
  черновик, проверяет срок, доступ, ревизию и точный snapshot, создаёт операцию, исходные итоги,
  запись аудита, приватный план и outbox, затем удаляет plaintext черновик и строку подтверждения.
  Значение токена остаётся только частью namespaced `idempotency_key` операции для точного повтора.
  Повтор по `confirmation:<token>` возвращает ту же операцию
  до поиска удалённого после изменения черновика токена. Нулевая допустимость использует отдельный
  ключ `zero:<draftId>:<revision>`, повторную проверку сохранённого snapshot и завершённую операцию
  без сообщения в Queue.
- Полные команды, фильтр, сортировка, исходные и целевые значения хранятся только в приватном
  зашифрованном плане. AES-GCM использует случайный 96-битный nonce и отдельный 256-битный ключ
  `OPERATION_PLAN_KEY_V1`. AAD связывает назначение, версию, портал, владельца, черновик, ревизию
  и токен. Ключ не хранится в Supabase, ответах или журнале и должен сохраняться до окончания срока
  хранения планов и защищённых предыдущих значений. Ротация требует нового key version и чтения
  старых версий до удаления соответствующих записей. Предыдущие значения по согласованному выбору
  продукта хранятся в отдельной зашифрованной записи Supabase, а не внутри Битрикс24.
- Outbox содержит стабильные `messageId`, `operationId`, `launchAttempt` и `portalId`. Повтор
  отправки использует то же сообщение. Ошибка отправки переводит ещё не захваченную операцию в
  `launch_failed`; контролируемый повтор использует тот же ID операции и ключ с новым attempt.
  Cron восстанавливает pending и застрявшие launching после конечных Queue retries/DLQ.
  До реализации исполнения в задаче 022 consumer не подтверждает `operation.execute`; запись
  остаётся launching, пользовательские задачи не меняются.
- Краткий owner-scoped receipt возвращает актуальный статус операции после отправки без права
  просмотра отчётов. Повтор отправки требует отдельного `retry_operations`; SQL ещё раз сверяет
  версию доступа под блокировкой. Если ответ запуска потерян, подтверждённый токен сохраняется в
  текущем UI и после истечения срока используется только для поиска уже созданной операции.
- Публичная запись операции сохраняет только служебные счётчики, IDs задач и полей, без полных
  команд и значений. Отчётные записи для исключённых/неизменяемых задач содержат допустимые
  названия, ссылки и причины, но не значения полей.
