# Обсуждение реализации: задача 002

Дата: 2026-08-06  
Статус: обсуждение продолжается  
Текущая задача: **002. Настроить Cloudflare Workers и локальные bindings**.

Источник задачи: `tasks/002-cloudflare-local-runtime.md`.

## Цель задачи 002

Создать локальный Cloudflare-контур, совместимый с будущим production-контуром, без раскрытия секретов:

- API Worker;
- отдельный Queue consumer Worker;
- Queue;
- временное R2-хранилище отчётов;
- Cron;
- server-only переменные окружения и шаблон `.dev.vars.example`;
- понятная ошибка при неполной конфигурации.

На момент записи бизнес-логика операций, Queue consumer, авторизация и интеграции ещё не реализованы. Задача 002 создаёт техническую основу для их безопасной реализации и локальной проверки.

## Принятые решения

### 1. Неполная конфигурация — вариант C

Применяется модель уровней готовности:

- базовый интерфейс не ломается из-за отсутствия ещё не используемой интеграции;
- недоступные подсистемы заранее показываются как недоступные;
- критичные серверные маршруты дополнительно проверяют конфигурацию;
- пользователь не видит названия переменных, токены и другие технические детали;
- администратор может получить диагностическое состояние без значений секретов.

### 2. Queue не подтвердила запуск — вариант B

После подтверждения операции при неопределённом результате постановки:

1. Интерфейс показывает «Проверяем запуск».
2. Сервер проверяет, подтверждена ли постановка.
3. При подтверждённом запуске показывается обычный прогресс.
4. При неподтверждённом запуске операция получает состояние «Ошибка запуска».
5. Повтор использует ту же операцию и тот же идемпотентный ключ.

Операция не получает ложный статус «Выполняется», пока Queue не подтвердила запуск.

### 3. Consumer недоступен после принятия сообщения — вариант B

Если Queue уже приняла операцию, но consumer временно недоступен:

- операция остаётся `Выполняется`;
- интерфейс показывает «Временно ожидает обработки» и время последнего прогресса;
- выполненные изменения и результаты сохраняются;
- после 30 минут без серверного прогресса операция получает `Прервана`;
- оставшиеся задачи получают `Не обработана`;
- формируется частичный отчёт;
- автоматическое возобновление после `Прервана` запрещено.

Отсчёт ведётся от последнего сохранённого результата или подтверждённой активности consumer, а не от браузера пользователя.

### 4. Закрытие вкладки или потеря сети — вариант B

После подтверждения операция выполняется на сервере и не зависит от открытой вкладки:

- закрытие вкладки не отменяет операцию;
- пользователь после возвращения видит актуальный прогресс или итог;
- отмена возможна только отдельным явным действием;
- пока операция не достигла конечного статуса, новая массовая операция этого пользователя не запускается.

Это решение отменяет противоречащее положение PRD о прекращении операции при закрытии браузера.

### 5. Изменение прав во время операции — вариант B

Права проверяются перед изменением каждой задачи:

- при отзыве общего доступа пользователя к приложению или операции текущая задача доводится до фактического результата, новые не начинаются, операция получает `Прервана`;
- при потере доступа только к одной задаче она получает `Ошибка` с безопасной причиной, остальные задачи продолжают обрабатываться;
- остаток при глобальном отзыве получает `Не обработана`;
- отзыв прав и прерывание фиксируются в аудите.

### 6. Отказ интеграции во время операции — вариант B

Ошибки разделяются по устойчивости:

- `429`, `5xx` и сетевые сбои — временные, для них применяются ограниченные автоматические повторы;
- первый `401` допускает одну серверную попытку обновить авторизацию;
- повторный `401`, устойчивый отказ авторизации или недействительные credentials прерывают дальнейшую обработку;
- недоступность Supabase прекращает новые изменения, потому что без сохранения результата, идемпотентности и аудита продолжать небезопасно.

Пользователь видит нейтральную системную ошибку, без названий secrets, токенов и тел технических ответов.

### 7. Неопределённый результат записи в Bitrix24 — вариант C

Если запрос оборвался, но Bitrix24 мог применить изменение:

1. Запись не повторяется вслепую.
2. Система повторно читает фактическое состояние задачи.
3. Если цель уже достигнута — результат `Успешно`.
4. Если изменения нет, а исходная версия не изменилась — допускается безопасный повтор той же детерминированной команды.
5. Если задача изменилась иначе — результат `Конфликт`.
6. Если итог нельзя подтвердить после ограниченных попыток — результат `Ошибка`.

Для относительных операций сохраняется рассчитанное конечное значение. Например, повторяется не «прибавить три дня», а «установить дату X».

### 8. Отмена во время обработки — вариант C

Отмена происходит на границе каждой задачи:

- сервер сохраняет идемпотентный флаг отмены;
- интерфейс показывает `Отменяется`;
- уже отправленный запрос к Bitrix24 не обрывается и получает фактический результат;
- новые задачи не начинаются;
- остаток получает `Не обработана`;
- операция становится `Отменена`, формируется частичный отчёт;
- повторная доставка Queue не возобновляет отменённую операцию;
- повторный клик «Отменить» не создаёт новых событий.

## Текущий незакрытый edge case

### 9. Две вкладки или два устройства запускают операции одновременно

Рекомендованный вариант: блокировать второй запуск, пока первая операция не достигла конечного статуса.

Техническая опора:

- один идемпотентный ключ подтверждения для защиты от двойного клика, обновления страницы и повторного HTTP-запроса;
- ограничение базы данных: не более одной активной операции на пользователя;
- к активным относятся `Проверяем запуск`, `Выполняется`, `Временно ожидает обработки`, `Отменяется`;
- вторая вкладка показывает текущую активную операцию и ссылку на её детали.

Варианты для фиксации:

- A — заблокировать второй запуск и показать активную операцию;
- B — поставить вторую операцию в ожидание;
- C — отменить текущую и заменить её новой.

Рекомендация: A.

## Технические решения для задачи 002

- Разделить API Worker и consumer Worker.
- Связать API Worker с Queue как producer, consumer Worker — как consumer.
- Настроить локальную эмуляцию Queue и R2 с сохраняемым локальным состоянием.
- Настроить тестовый Cron без бизнес-эффектов.
- Добавить Dead Letter Queue для сообщений, исчерпавших повторные попытки.
- Хранить секреты только в server-only `.dev.vars` локально и Workers Secrets в production.
- Не возвращать значения и имена секретов в пользовательских API-ошибках.
- Подготовить локальные сценарии остановки/restart consumer, повторной доставки Queue, отсутствующей конфигурации и вызова Cron.
