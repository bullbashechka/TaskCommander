# Решения реализации: задача 006

Дата: 2026-08-11  
Статус: утверждено  
Текущая задача: **006. Реализовать серверный слой доступа к данным**.

Источник: `tasks/006-data-access-layer.md`.

## Граница задачи

Задача создаёт server-only доступ к Supabase, репозитории, транзакционные RPC и
пагинацию. Она не добавляет UI, Bitrix24 API, Queue consumer, append-only writer
аудита или полный граф статусов операции.

## Зафиксированные правила

1. Устаревшая вкладка не перезаписывает черновик: применяется optimistic concurrency
   по `revision`.
2. Повтор сетевого запроса использует тот же ключ идемпотентности; полноценный replay
   создания операции реализуется в задаче 008.
3. Ошибка отдельной задачи не останавливает остальные; системная недоступность
   прекращает новые изменения.
4. Частично применённая задача повторяет только неприменённые поля после новой проверки.
5. Отзыв общего права останавливает дальнейшую обработку; потеря доступа к одной задаче
   даёт локальный безопасный результат.
6. История и аудит используют стабильный временной срез и курсорную пагинацию.
7. Отсутствующий и недоступный объект имеют единый публичный результат.
8. Предыдущие значения доступны только механизму восстановления после повторной проверки
   прав; обычные репозитории их не читают.
9. Итоговые счётчики изменяются только вместе с новой уникальной строкой результата.
10. При неопределённом результате Bitrix24 повторная обработка сначала сверяет фактическое
    состояние; правила реализуются в consumer задачи 022.
11. Истёкший черновик заменяется только явным сохранением с повторной проверкой.
12. При недоступном Supabase изменение задач не начинается.
13. У пользователя одновременно выполняется одна операция; подготовка нового черновика
    разрешена.
14. Временный несохранённый ввод хранится только в рамках текущей сессии интерфейса;
    UI-реализация относится к задачам 016–020.
15. Критическое внутреннее действие и аудит должны фиксироваться одной транзакцией;
    writer аудита добавляется задачей 007.
16. Одинаковые имена личных фильтров конфликтуют после нормализации; замена требует
    актуальной ревизии.
17. При деактивации удаляются рабочие персональные данные, история сохраняется; это
    реализует задача 012.
18. Восстановление не перезаписывает последующие изменения; это реализует задача 025.
19. Изменение целевого поля после preflight блокирует всю задачу как конфликт; это
    реализуют задачи 019 и 022.
20. Черновик хранит снимок фильтра и сортировки, а не ссылку на изменяемый фильтр.

## Техническая модель

- Supabase service-role key доступен только Worker через обязательные Secrets.
- Все пользовательские запросы получают `portalId`, `actorId` и эффективные права.
- Доступ к собственным сущностям всегда фильтруется парой `portal_id + actor_id`.
- `view_all_reports` расширяет видимость операций и отчётов внутри портала;
  `view_audit` открывает журнал аудита.
- `record_task_processing_result` атомарно сохраняет результат, optional protected payload
  и счётчики. Повтор идентичного результата не меняет счётчики.
- Результаты разных задач фиксируются независимыми транзакциями.
- SQL функции доступны только service-role; `anon`, `authenticated` и `public` не получают
  права выполнения.
