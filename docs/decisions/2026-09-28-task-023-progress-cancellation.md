# 023: Progress, cancellation, and worker liveness

## Decision

The progress API returns only the current owner's operation. It reads persisted operation counters and `stateVersion`; `processed` sums recorded eligible-task outcomes, including `not_processed`, and the percentage uses eligible tasks as its denominator. A separate owner-scoped, cursor-paginated feed returns at most 100 persisted task outcomes per request, with safe titles and links and any later result refinement. It is a bounded progress feed, not the operation history planned for task 028. Browser polling does not own or renew an execution. Reopening `/operations` reads the latest owned operation; `/operations/:operationId` reads that exact operation without launching it again.

Cancellation requires the owner's current `app_access` and `run_bulk_operations` permissions. The database verifies owner and access version in the same transaction as the stop request. A running operation without an execution lease and without an unresolved write finalizes immediately. An unresolved write is classified by the watchdog before finalization. With an active lease, the consumer finishes the current task, records its result, and finalizes the rest as `not_processed`. Closing the browser does not request cancellation.

Each Queue delivery acquires a server-owned, attempt-fenced execution lease for three minutes. The consumer renews it every 30 seconds, including the active task claim, but stops renewal after five minutes without a persisted task outcome or a previously completed claim. Before a result or claim-release RPC, it drains any active heartbeat and renews only the operation lease; the claim may already be `done` or deleted before that RPC returns. A duplicate delivery cannot steal the lease. At the 100-task continuation boundary, the worker releases its lease before sending the next Queue message; a failed send remains recoverable through the existing no-lease redrive path. A retryable failure releases the lease so that path can resume the same attempt. A lost delivery leaves its lease behind. The scheduled watchdog terminates an expired lease; writing or applied claims without a recorded result become `unconfirmed`, while untouched tasks become `not_processed`. An applied claim retains its encrypted before-values and may later be refined from a confirmed mock read. It also finalizes a stop request left without a lease. An expired lease is never redriven blindly. A late adapter response cannot record a result or claim another task after the worker loses its lease.

The local mock CAS checks the terminal operation state, so a late mock write after watchdog interruption is rejected. Real Bitrix24 behavior remains unverified until a portal exists. A remote request already in flight at lease expiry may still complete; its task remains `unconfirmed` rather than being reported as untouched. Neither the progress screen nor the audit trail includes protected previous values.
