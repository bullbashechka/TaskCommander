# 024: Retry operation

## Decision

A retry creates a new operation after fresh task preflight and explicit confirmation. Eligible source outcomes are `error`, `unconfirmed`, `conflict`, `not_processed`, and `partially_applied`; a refinement overrides the original outcome. `canRetry` is a display hint and does not select tasks. For a partial result, only effective failed fields are requested. Excluded, unchanged, and successful source tasks are never selected.

The server reads the terminal source operation and its encrypted execution plan through a service-role-only RPC after checking current permissions. An owner needs `retry_operations` and `view_own_reports`; another operator needs `retry_operations` and `view_all_reports`. Both need app access, permission to run and change fields, and fresh field scope. The source must remain terminal, unarchived, and within retention. Its `stateVersion` fences task-result refinements between selection and launch. A retry of a retry uses that immediate source plan's per-task targets, preserving distinct task goals through successive generations.

When a source report row exists, it must still have `storage_status=active`; `archived_pending_artifact` is unavailable even before `archived_at` is set. Only the fields in the selected per-task retry intents must fit the current allowed field scope. Source commands for successful fields are never copied into a retry draft, response, or new encrypted plan. The draft's global commands are normalized absolute metadata derived from the selected intents; per-task targets remain authoritative. A revoked, refined, archived, or newly out-of-scope retry draft is withheld with HTTP 409. Only such a stale retry draft may be replaced atomically by a fresh retry; an unrelated live draft stays intact. Replacing a stale draft also revokes its confirmation. An operator who retains ordinary bulk editing rights after losing `retry_operations` can read only the retry draft's ID and revision through a recovery endpoint, then discard that exact retry draft with a database CAS. The endpoint never returns its values and cannot delete a normal draft.

Each selected task stores a validated array entry containing its task ID and absolute target values. No numeric field mask is used. The targets come from the source preview rather than rerunning relative shift/add/remove commands; an ambiguous prior write is reread and compared with these absolute targets. The new preflight checks current values, editability, related records, access, and conflicts per task. A no-change or excluded task remains visible in the preview. The encrypted private plan contains per-task intent; the public operation stores field identifiers and counters only. The draft and its plaintext target values are deleted in the same transaction that creates the new operation, initial results, audit event, and durable Queue dispatch. The resulting operation has type `retry` and a `sourceOperationId` link.

An exact launch replay returns the same operation by the namespaced confirmation key, even after the draft is deleted. The database locks and rechecks source state, retention, owner permissions, field scope, confirmation, and draft revision before creating a new operation. A different or expired source forces a new preparation. A live unrelated draft is preserved.

An awaiting-confirmation retry draft can be rechecked by submitting its current revision. This rereads tasks and advances the revision; the previous confirmation is revoked by the draft trigger. Retrying an in-flight request with its prior revision still returns only its exact stored preview. Rollback deletes unlaunched retry drafts and confirmation rows before restoring the older launch function, preventing old relative commands from being used on those drafts.

## Verification boundary

SQL, Worker, and UI regression tests are authored but not executed by the agent under repository instructions. The user runs `bun run check` and `bun run db:docker:test`. Real Bitrix24 execution is not verified because no portal is available.
