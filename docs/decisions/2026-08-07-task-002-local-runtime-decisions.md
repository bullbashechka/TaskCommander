# Задача 002: решения по локальному Cloudflare runtime и эксплуатационным edge cases

Дата: 2026-08-07

Статус: утверждено

Задача: `tasks/002-cloudflare-local-runtime.md`

## Назначение документа

Этот документ фиксирует продуктовые и технические решения, принятые при разборе edge cases задачи 002. Он является каноническим источником решений по локальному Cloudflare runtime и ограничениям, которые этот runtime должен заложить для последующих задач.

Документ заменяет незавершённый черновик `docs/decisions/2026-08-06-task-002-discussion.md`. Общая архитектура продукта остаётся в `docs/superpowers/specs/2026-08-06-task-commander-design.md`, а полный объём задачи и критерии приёмки — в `tasks/002-cloudflare-local-runtime.md`.

Большая часть описанного пользовательского поведения реализуется не в задаче 002. Задача 002 создаёт изолированный локальный контур, на котором это поведение можно безопасно разрабатывать и проверять.

## Итоговая архитектура локального runtime

```text
Browser -> API Worker -> local Queue -> Consumer Worker
                    \-> local R2

local test Cron Trigger -> Worker scheduled handler
```

- API Worker обслуживает HTTP/API и статические assets, публикует сообщения в Queue и имеет R2 binding.
- Consumer Worker является отдельным auxiliary Worker, получает сообщения Queue и не предоставляет публичный пользовательский HTTP API.
- Оба Worker запускаются одним Vite/Miniflare-контуром и используют общие локальные Queue, DLQ и R2.
- Cron handlers в задаче 002 являются безопасными техническими пробами без бизнес-эффектов.
- Бизнес-обработка операций, Bitrix24-вызовы, отчёты и восстановление зависших операций остаются последующим задачам.

## Реестр принятых решений

### D1. Неполная конфигурация: уровни готовности

Выбран вариант C — раздельная готовность подсистем.

- Базовая оболочка приложения может работать без ещё не используемых интеграций.
- Недоступное действие блокируется до нажатия и объясняет, какая подсистема не настроена.
- HTTP, Queue и Cron проверяют только необходимую им конфигурацию, но делают это независимо друг от друга.
- Критически отсутствующая базовая конфигурация блокирует приложение целиком.
- Пользователь не видит имён переменных, токенов или значений secrets.
- Администратор получает безопасную диагностику с идентификатором события, но без значений secrets.

Задача 002 реализует bindings, проверку server-only конфигурации и readiness API. Пользовательские экраны готовности реализуются в последующих UI-задачах.

Это решение уточняет критерий `tasks/002-cloudflare-local-runtime.md`, требующий ошибки запуска при отсутствии обязательного secret. Глобальная startup-проверка заменяется проверкой обязательной конфигурации конкретной подсистемы: базовый runtime запускается, но HTTP, Queue или Cron handler отклоняет действие, если отсутствует обязательная именно для него конфигурация.

### D2. Queue не подтвердила постановку операции

Выбран вариант B — короткая проверка результата запуска.

- После подтверждения интерфейс показывает `Проверяем запуск`.
- Операция не получает ложный статус `Выполняется` до подтверждённой постановки.
- При подтверждённой постановке начинается обычное выполнение.
- При неподтверждённой постановке операция получает конечное состояние `Не запущена`; пользовательская формулировка — `Ошибка запуска`.
- Ручной повтор использует тот же operation ID и idempotency key.
- Повтор HTTP-запроса, обновление страницы и двойной клик не создают вторую операцию.
- Поздно доставленное сообщение проверяет состояние операции и не выполняет `Не запущенную` операцию.

Cloudflare Queue не используется как источник для прямого поиска сообщения. Согласование результата выполняется через устойчивое состояние операции и попытки постановки. Конкретный механизм относится к задачам 008 и 021.

### D3. Queue приняла сообщение, consumer временно недоступен

Выбран вариант B — двухступенчатая модель.

- Операция остаётся `Выполняется`.
- UI показывает `Временно ожидает обработки`, время последнего серверного прогресса и уже сохранённые результаты.
- Queue и consumer выполняют ограниченные автоматические повторы.
- Через 30 минут без сохранённого результата задачи или подтверждённой активности consumer операция получает `Прервана`.
- Обработанные задачи сохраняют фактические результаты.
- Остаток получает `Не обработана`.
- Формируется частичный отчёт.
- После `Прервана` автоматическое возобновление запрещено; повтор является новой явно подтверждённой операцией.

Отсчёт ведётся от серверного `last_progress_at`, а не от активности браузера.

### D4. Закрытие вкладки или потеря пользовательской сети

Выбран вариант B — продолжать операцию на сервере.

- После подтверждения операция не зависит от вкладки или устройства.
- Закрытие страницы и временная потеря сети ничего не отменяют.
- После возвращения пользователь видит актуальный прогресс или итог.
- Пока операция активна, новая массовая операция этого пользователя блокируется.
- Остановка возможна только отдельной явной командой отмены.

Это решение сознательно заменяет требование `PRD.md`, согласно которому потеря браузера прекращает обработку после текущей задачи. PRD и задача 023 должны быть приведены к серверной Queue-модели: lease означает активность consumer, а не heartbeat вкладки.

### D5. Права изменились во время операции

Выбран вариант B — различать глобальный и локальный отказ.

- Права перепроверяются непосредственно перед изменением каждой задачи.
- Потеря доступа только к конкретной задаче даёт этой задаче `Ошибка`; остальные задачи продолжают обрабатываться.
- Потеря общего доступа к приложению или права выполнять операцию завершает текущую задачу до фактического результата и запрещает запуск новых.
- Операция получает `Прервана`, остаток — `Не обработана`.
- Отзыв прав и прерывание операции фиксируются отдельными аудит-событиями.

Подробная реализация относится к задачам 010, 012, 022 и 023.

### D6. Временный и постоянный отказ интеграции

Выбран вариант B — классифицировать причину.

- `429`, `5xx`, timeout и connection reset считаются временными техническими ошибками и получают ограниченный retry.
- Первый `401` вызывает одну серверную попытку обновления или перепроверки авторизации.
- Повторный `401` либо устойчивые invalid credentials запрещают запуск новых задач и прерывают операцию.
- `403` для одной задачи является локальной ошибкой этой задачи.
- Глобальный `403` либо потеря общего права прерывает операцию.
- При недоступном Supabase новые изменения немедленно прекращаются: без устойчивой записи нельзя гарантировать результат, аудит и идемпотентность.
- Пользователь видит безопасную формулировку и идентификатор события; внутренние ответы и credentials не раскрываются.

Число retry и интервалы относятся к задачам 022 и 031, а не к задаче 002.

### D7. Bitrix24 мог применить изменение, но ответ потерян

Выбран вариант C — сначала проверить фактическое состояние.

- После timeout или connection reset запись не повторяется вслепую.
- Consumer повторно читает задачу и сравнивает её с заранее рассчитанным целевым состоянием.
- Цель уже достигнута — `Успешно`.
- Изменение не применено, исходная версия прежняя — допустим ограниченный безопасный повтор детерминированной команды.
- Задача изменилась иначе или только частично — `Конфликт`.
- Фактический итог невозможно подтвердить после ограниченных попыток — `Ошибка` с безопасной формулировкой.
- Для относительного изменения сохраняется конкретное целевое значение. Команда вида `+3 дня` не вычисляется заново после timeout.
- Для множественных полей сравнивается полный нормализованный набор.

Реализация относится к задачам 018, 019, 022 и 024.

### D8. Явная отмена во время обработки

Выбран вариант C — отмена на границе каждой задачи.

- Сервер атомарно и идемпотентно сохраняет `cancel_requested`.
- UI показывает `Отменяется`.
- Если запись текущей задачи ещё не началась, она не запускается.
- Уже отправленный запрос не обрывается и не откатывается; сохраняется его фактический результат.
- Consumer проверяет отмену перед каждой задачей, даже внутри полученного batch.
- Новые задачи не начинаются, остаток получает `Не обработана`.
- Итоговый статус — `Отменена`; создаётся частичный отчёт.
- Повторная доставка Queue не возобновляет отменённую операцию.
- Повторная отмена является no-op и не дублирует аудит.

Реализация относится к задачам 008, 022, 023 и 026.

### D9. Конкурентный запуск из вкладок или устройств

Выбран вариант A — блокировать второй запуск.

- У пользователя может быть только одна активная операция.
- Активными считаются `Проверяем запуск`, `Выполняется`, `Временно ожидает обработки` и `Отменяется`.
- Вторая вкладка или устройство показывают текущую операцию и переход к её деталям.
- Один idempotency key защищает от double-click, refresh и повторного HTTP после timeout.
- Уникальное ограничение базы данных защищает от двух разных intent одного пользователя.
- Вторая операция не ставится в ожидание и не заменяет первую.

Реализация относится к задачам 008 и 021.

### D10. `Не запущена` и единственный слот пользователя

Выбран вариант A — освобождать слот.

- После окончательной `Ошибки запуска` операция получает конечное состояние `Не запущена`.
- Пользователь может подготовить и подтвердить другую операцию.
- Повтор старой операции остаётся доступным из истории, но блокируется, если уже существует другая активная операция.
- Позднее сообщение старой операции не выполняется, поскольку consumer обязан проверять её текущее состояние.

`Не запущена` является отдельным конечным доменным статусом операции. Он должен быть добавлен в контракты и машину состояний задач 003 и 008. Пользовательская формулировка этого статуса — `Ошибка запуска`.

### D11. Операция завершена, но отчёт не готов

Выбран вариант B — независимые статусы операции и файлов.

- Операция сразу получает фактический конечный статус независимо от XLSX, CSV, R2 и Bitrix24 Disk.
- Для XLSX и CSV существуют отдельные записи и состояния: `Формируется`, `Ожидает выгрузки`, `Готов`, `Ошибка`.
- Ошибка одного формата не блокирует другой.
- Временные ошибки генерации и выгрузки повторяются ограниченно.
- Итоговое уведомление отправляется по завершении операции и ведёт на стабильную внутреннюю карточку, а не на временную ссылку R2.
- Права повторно проверяются при каждом скачивании.
- Если R2-объект утрачен до подтверждённой загрузки в Bitrix24 Disk, файл повторно строится из сохранённых результатов операции.
- R2 удаляется после подтверждённой загрузки либо по TTL.

Реализация относится к задачам 026, 027, 029 и 031.

### D12. Изоляция local от production

Принято обязательное техническое решение: стандартный локальный запуск полностью изолирован.

- Local bindings имеют `remote: false`.
- Vite/Miniflare запускается с отключёнными remote bindings.
- Обычные project scripts не содержат `--remote`, deploy или неявный production environment.
- Local-конфиги не содержат production account ID, resource ID, routes или service bindings.
- Используются отдельные local имена Workers, Queue, DLQ и R2.
- Наличие Cloudflare API token в окружении не меняет режим запуска.
- `APP_ENV=local` разрешает только mock Bitrix adapter.
- Разрешённый Supabase development-проект задаётся явным local allowlist; его нельзя надёжно определить как development по формату URL.
- Local runtime сравнивает настроенный Supabase project reference или нормализованный host с allowlist и отклоняет readiness/запуск при несовпадении.
- Staging/production workflow и production secrets создаются только в задаче 035.

### D13. Сохраняемое локальное состояние и совместимость

Выбран вариант C — persistent state с инфраструктурной версией и quarantine.

Точный корень состояния:

```text
.wrangler/state/task-commander-local
```

Первая инфраструктурная эпоха:

```text
Queue: task-commander-local-operations-v1
DLQ:   task-commander-local-operations-dlq-v1
R2:    task-commander-local-reports-v1
Key:   v1/<operation-id>/<format>/<artifact-id>
```

- Queue и R2 переживают перезапуск локального runtime.
- Несовместимое изменение инфраструктурной схемы создаёт новую эпоху, например `v2`.
- Новый код не читает ресурсы старой эпохи и не удаляет их автоматически.
- Минимальное probe-сообщение задачи 002 содержит `schemaVersion`, `messageId`, `kind`, `createdAt` и `payload`.
- Неизвестные версия или kind не достигают handler с побочными эффектами и после ограниченных попыток попадают в DLQ.
- Ошибка может содержать message ID и schemaVersion, но не полный payload или secrets.
- Полный доменный Queue envelope остаётся задачам 003, 021 и 022.

### D14. Безопасный сброс local state

- Предоставляется отдельная команда `dev:reset`.
- Удаляется только `<repo>/.wrangler/state/task-commander-local`.
- Скрипт определяет корень репозитория по собственному расположению, нормализует абсолютный путь и проверяет точное ожидаемое относительное соответствие.
- При любом несовпадении удаление отклоняется.
- Запрещены glob, `$HOME`, `%USERPROFILE%`, workspace root, пользовательский target, вся `.wrangler` и родительский `.wrangler/state`.
- `.dev.vars`, fixtures и соседние state-каталоги не удаляются.
- Повторный reset при отсутствующем каталоге является успешным no-op.

## Формальные расхождения с текущими требованиями

### Закрытие браузера

`PRD.md` и задача 023 связывают потерю клиента с остановкой. Принято противоположное решение: подтверждённая Queue-операция продолжает выполняться на сервере. PRD и задача 023 требуют последующего обновления.

### Момент перехода в `Выполняется`

Задача 021 предполагает `Выполняется` сразу после валидного подтверждения. Принято уточнение: сначала используется `Проверяем запуск`, а `Выполняется` устанавливается только после подтверждённой постановки.

### Дополнительные состояния

В текущем PRD отсутствуют `Проверяем запуск`, `Не запущена`, `Временно ожидает обработки` и `Отменяется`. Задача 003 должна разделить формальные доменные статусы и UI-подсостояния. Неизвестные состояния не должны проникать в контракты неявно.

### Heartbeat и lease

Клиентский heartbeat не управляет жизнью серверной операции. Для определения зависания используется серверный прогресс или heartbeat consumer. Потеря браузера не меняет статус операции.

### Уведомление до готовности файла

Требуемая PRD ссылка на отчёт ведёт на заранее созданную внутреннюю карточку. XLSX и CSV могут продолжать формироваться после отправки итогового уведомления.

### Проверка обязательных secrets

Критерий задачи 002 требует ошибку запуска при отсутствии обязательного secret. Принято уточнение: обязательность определяется отдельно для каждой подсистемы. Отсутствие ещё не используемой интеграции не блокирует базовый runtime, но блокирует любой HTTP, Queue или Cron handler, которому эта интеграция необходима.

## Что обязана реализовать задача 002

- отдельные конфигурации API Worker и auxiliary consumer Worker;
- Queue producer, Queue consumer и DLQ bindings;
- закрытый R2 binding;
- безопасные probe handlers для Queue, R2 и Cron без бизнес-эффектов;
- локальные non-secret vars и шаблон `.dev.vars.example`;
- server-only проверку конфигурации для HTTP, Queue и Cron;
- readiness API без утечки secrets;
- единый persistent local state;
- инфраструктурную эпоху `v1` и минимальный version gate probe-сообщения;
- безопасный точный `dev:reset`;
- отдельное ephemeral test state;
- документацию локального запуска, persistence, DLQ, reset и запрета remote mode;
- проверку, что клиентский bundle, API-ответы, логи и тестовые snapshots не содержат secrets.

## Что задача 002 не реализует

- доменную машину состояний операции;
- реальную постановку массовой операции;
- Bitrix24 consumer и бизнес-retry;
- проверку пользовательских прав;
- пользовательскую отмену;
- генерацию и выгрузку отчётов;
- production Cloudflare resources и deployment;
- production OAuth и secrets;
- изменение PRD и downstream task-файлов.

Эти работы остаются задачам 003, 008–012, 018–024, 026–031, 033 и 035.

## Проверочные инварианты задачи 002

1. `bun run dev` работает без Cloudflare login и не обращается к production Cloudflare resources.
2. API Worker публикует probe-сообщение, auxiliary consumer получает его через локальную Queue.
3. Неизвестная версия probe-сообщения не выполняет побочных эффектов и попадает в локальную DLQ.
4. R2 put/get/delete выполняются только через локальный binding; bucket не публикуется.
5. Queue и R2 переживают остановку и повторный запуск.
6. `dev:reset` удаляет только точный local state Task Commander и сохраняет `.dev.vars` и соседние каталоги.
7. Тесты не читают и не меняют persistent dev state.
8. Cron probe вызывается локально и не создаёт бизнес-событий или ложный аудит.
9. Отсутствующая обязательная конфигурация даёт безопасную ошибку без значения secret.
10. Имена и значения server secrets отсутствуют в клиентском bundle, API-ответах, логах и snapshots.
11. Репозиторий не содержит `remote: true`, `--remote`, production routes или production resource IDs в local-конфигурации.
12. Local runtime отклоняет Supabase endpoint, project reference или host, отсутствующий в явном local allowlist.
