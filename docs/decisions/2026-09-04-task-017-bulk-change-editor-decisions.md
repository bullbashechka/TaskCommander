# Решения задачи 017: редактор массовых изменений

## Граница авторизации

- Каталог редактирования отделён от каталога фильтрации. Сервер возвращает только пересечение
  поддерживаемых и редактируемых возможностей адаптера Bitrix24 с личным `fieldScope`.
- Чтение каталога и черновика требует `app_access`, `run_bulk_operations` и
  `change_allowed_fields`. Сохранение повторяет эту проверку и заново строит каталог; данные
  браузера не считаются доказательством права.
- Нативная редактируемость конкретной задачи не вычисляется на этом шаге. Её повторная проверка
  вместе со статусом и версией задачи относится к preflight задачи 019.
- Завершение задач, вложения, комментарии, чек-листы, шаблоны, повторения, создание и удаление не
  входят в каталог. Значение завершённого статуса также удаляется из вариантов и отклоняется
  серверной семантической проверкой.

## Контракт изменений

- Скалярный тип значения связан с `kind`: текст не принимает boolean, число должно быть конечным,
  пользователь задаётся Bitrix ID. Коллекции не принимают пустые или повторяющиеся значения.
- Доступные действия выводятся из формы поля: одиночные поля поддерживают `set`, даты также
  `shift`, коллекции — `replace`, `add`, `remove`, nullable-поля — `clear`.
- Один черновик содержит не более одного изменения каждого поля. Сервер сверяет kind, action и
  option values с актуальным каталогом перед записью.
- Каталог не наследует лимиты операции: число доступных полей и вариантов enum не ограничивается
  лимитами 64 изменения и 256 значений в одной команде.
- Размер `changes` проверяется по безопасной верхней границе текстового представления PostgreSQL
  `jsonb`, включая пробелы структурных разделителей и разворачивание чисел из экспоненты.
- Относительный сдвиг явно хранит направление, число дней и календарь. Расчёт результата для
  каждой задачи остаётся в задаче 018.

## Черновик и переход между этапами

- Выбранные ID передаются редактору внутри текущего React workflow и не помещаются в URL,
  `localStorage` или `sessionStorage`.
- Новый черновик создаётся только после появления хотя бы одного валидного изменения, потому что
  схема БД запрещает selection-only draft. До сохранения выбор остаётся в состоянии страницы.
- Существующий 24-часовой черновик не восстанавливается автоматически. Пользователь явно выбирает
  продолжение либо замену текущим набором задач.
- Сохранение использует optimistic concurrency по `revision`. Любая запись принудительно задаёт
  статус `preparing` и очищает `preflight_snapshot`; browser request не принимает status,
  confirmation или owner.
- Черновик сохраняет канонические filters и sort вместе с selection и changes. Это позволяет
  явному восстановлению продолжить тот же контекст отбора.
- После смены effective-access редактор получает новый каталог. Исчезнувшие поля удаляются, а
  несовместимые действия сбрасываются; новую ревизию пользователь сохраняет явно.

## Интерфейс

- Экран следует утверждённой двухколоночной структуре: слева ограниченный список добавленных полей,
  справа одна активная настройка. Это не показывает одновременно все возможные элементы сложной
  формы и сохраняет причинный порядок «поле → операция → значение».
- Семантика `replace`, `add`, `remove`, `clear` и относительного сдвига описывается рядом с вводом.
  Пользователь видит число задач и число изменяемых полей до сохранения.
- Сохранение черновика не запускает preflight и не изменяет задачи. Расчёт, проверка, preview и
  подтверждение относятся к задачам 018–020.
