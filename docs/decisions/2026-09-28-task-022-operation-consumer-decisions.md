# Решения задачи 022: выполнение операций

- Queue-сообщение содержит только идентификаторы операции и попытки. Consumer читает план из
  Supabase, расшифровывает AES-GCM с AAD, связанным с порталом, владельцем, черновиком, ревизией и
  токеном подтверждения. Устаревшая попытка не начинает обработку.
- Перед каждым изменением consumer повторно читает состояние задачи, права инициатора и доступность
  связанных пользователей и проекта. Значимая версия preflight проверяется до записи. Ошибки
  отдельной задачи дают отдельный результат; временные сбои чтения и rate limit оставляют задачу
  для Queue retry. Cron повторно публикует застрявшую работающую операцию с тем же сообщением.
- SQL-claim хранится до внешней записи. После перехода в `writing` просроченный claim требует
  перечитывания, а не слепой второй записи. Для локального mock Supabase CAS дополнительно проверяет
  UUID claim, попытку, срок lease, актуальные права и монотонную версию всей задачи. Поэтому
  неопределённый ответ можно сопоставить с устойчивым результатом записи. Реальный Bitrix-адаптер
  отсутствует; это поведение проверяется на тестовых данных. Применение реального Bitrix в production
  остаётся непроверенным.
- Локальный mock хранит текущие тестовые задачи в Supabase для согласованности разных экземпляров
  API и consumer. Этот путь включён только при `APP_ENV=local` и `BITRIX_ADAPTER=mock`; SQL RPC
  доступны только сервисной роли. Состояние mock не является хранилищем реальных задач.
- Предыдущие значения шифруются до записи задачи отдельным AES-GCM payload с purpose-bound AAD.
  SQL сохраняет ciphertext в приватном claim и переносит его в `protected_task_result` атомарно с
  подтверждённым результатом. Неподтверждённый результат не выдаётся за успех и не становится
  восстанавливаемым без позднего подтверждения; атомарный RPC уточнения сохраняет ciphertext вместе
  с append-only уточнением. Ключ `OPERATION_PLAN_KEY_V1` должен сохраняться до истечения срока
  хранения планов и предыдущих значений.
- Счётчики и аудит меняет существующая SQL-машина состояний. Consumer подтверждает Queue-сообщение
  только после финализации или при устаревшей/терминальной попытке. Rollback удаляет только объекты
  этой миграции и выполняется внутри внешней тестовой транзакции.
- Версия значимого состояния вычисляется по тому же набору полей при preflight, повторном чтении и
  применении, включая парные даты; запись меняет только целевые поля. Сценарные изменения локального
  mock также сохраняются через CAS и повышают версию всей задачи.
- Ожидание портального rate slot завершается до перехода claim в `writing`; переход продлевает lease.
  После просрочки CAS запрещает позднюю запись. Точный повтор результата после `done` возвращает
  сохранённую запись, а расхождение создаёт аудируемый конфликт. Неисправимые ошибки плана, прав и
  каталога полей завершают попытку; неопределённый ответ после записи не повторяет запись вслепую.
