# Решения реализации: задача 015

Дата: 2026-09-04
Статус: реализовано

## Каталог и серверная проверка

- `GET /api/tasks/fields` возвращает версионированный каталог доступных полей: подпись, тип,
  множественность, nullable-семантику, допустимые операторы, сортируемость и источник значений.
- Каталог и варианты значений не получают прежний лимит 256 полей из модели делегированного
  доступа. Один поисковый или сохраняемый запрос ограничен 256 уникальными условиями в соответствии
  с существующей формой `saved_filter.filter_payload`.
- Каталог строится из явных фильтровых capability текущего Bitrix24-адаптера: подпись,
  сортируемость, источник значений и варианты не выводятся из идентификатора поля. Неподдерживаемые
  поля не попадают в ответ.
- `POST /api/tasks/search` проверяет сочетание идентификатора поля, типа, оператора и сортировки по
  тому же каталогу до обращения к поиску. Повторные условия одного поля отклоняются: несколько
  значений одного условия передаются одним массивом и означают `ИЛИ`.
- Поля постановщика, исполнителя, соисполнителей и наблюдателей остаются отдельными условиями.
  Безопасный поиск активных сотрудников доступен обычному пользователю приложения через
  `GET /api/tasks/users`; административные маршруты для этого не используются.

## Личные наборы

- CRUD доступен через `/api/tasks/saved-filters`. Идентификатор владельца не принимается от
  клиента; репозиторий всегда получает проверенный `DataAccessContext` и ограничивает данные парой
  `portal_id + actor_id`.
- Переименование изменяет только имя и не пересохраняет условие. Переименование и удаление используют
  актуальную `revision`. Конфликт устаревшей вкладки не перезаписывает новый вариант.
- Сохранённый набор содержит только условия фильтра, поскольку существующая таблица
  `saved_filter` и PRD определяют именно личный фильтр. Сортировка является состоянием текущего
  просмотра. Будущий черновик массовой операции сохраняет отдельные снимки фильтра и сортировки.
- Структурно повреждённый `filter_payload` не передаётся браузеру и преобразуется в безопасную
  ошибку недоступности. Структурно корректный, но семантически устаревший набор возвращается только
  его владельцу, чтобы тот мог переименовать или удалить запись. UI блокирует применение такого
  набора по текущему каталогу; поиск повторяет серверную проверку и не обращается к Bitrix24 с
  несовместимым условием.
- Для администратора Bitrix24 перед первой записью личного набора создаются только необходимые
  строки идентичности с неактивным доступом и пустыми разрешениями. Это не выдаёт доступ обычному
  пользователю и сохраняет внешний ключ владельца.
- Ограничение в 256 наборов на владельца обеспечивается транзакционной блокировкой и триггером БД,
  поэтому параллельные запросы не обходят лимит ответа API.
- Лимит наборов, занятое имя и конфликт ревизии имеют разные безопасные API-коды, чтобы UI не
  предлагал восстановление ревизии для другой причины отказа.

## Интерфейс и граница следующей задачи

- Панель формирует канонический запрос: строка поиска является одним условием `title contains`,
  разные поля соединяются через `И`, значения одного поля — через `ИЛИ`. Зафиксированное в решении
  задачи 014 исключение: `equals` для множественного поля сравнивает весь набор, а `not_equals`
  отрицает это сравнение; UI называет добавляемые элементы значениями набора.
- Зависимые элементы ввода меняются вместе с оператором; несовместимые значения очищаются. Даты
  из `datetime-local` преобразуются в ISO-момент UTC (`Z`), диапазоны проверяются на
  порядок границ.
- Экран показывает точное количество найденных задач и явно отделяет результат поиска от
  подтверждённой массовой операции.
- Таблица, пагинация и выбор задач остаются в задаче 016.
- Макетный пункт «Последние 30 дней» не реализован отдельным пресетом: PRD не определяет поле и
  границы такого периода. Даты задаются без скрытой семантики через динамический конструктор.

## Развёртывание и откат лимита

- Перед миграцией проверяется запрос
  `select portal_id, owner_id, count(*) from public.saved_filter group by portal_id, owner_id having count(*) > 256`.
  Такие записи согласованно сокращаются владельцем до лимита; автоматическое удаление или выбор
  «старейших» запрещены. Если данные не согласованы, миграция останавливается с
  `TC_SAVED_FILTER_LIMIT_LEGACY_ROWS` внутри транзакции и не оставляет частично созданных объектов.
- Безопасный технический откат ограничения не меняет пользовательские данные: удалить триггер
  `saved_filter_enforce_owner_limit`, затем функцию `public.enforce_saved_filter_owner_limit()` в
  одной транзакции. Откат схемы не отменяет уже принятые продуктовые ограничения и выполняется
  только перед исправленной roll-forward миграцией.
