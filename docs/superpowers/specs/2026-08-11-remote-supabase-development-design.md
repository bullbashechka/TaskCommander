# Удаленный контур Supabase для схемы Task Commander

## Контекст

Задача `005` создаёт схему PostgreSQL и миграции. Первоначальная реализация
предполагала локальный Supabase CLI с Docker. Для текущей разработки выбран
удаленный проект Supabase: миграции применяются через авторизованный Supabase
MCP, а приложение запускается локально. Docker не является требованием
текущего запуска, но SQL-структура проекта и документация должны сохранять
возможность локального Docker-контура для будущей open-source поставки.

## Цели

- Применить версионированную миграцию схемы `Task Commander` в выбранный
  удаленный проект Supabase.
- Подтвердить на удаленной базе наличие таблиц, ограничений и RLS-политик,
  требуемых задачей `005`.
- Не передавать и не сохранять строку подключения PostgreSQL, пароль,
  service-role ключ или OAuth-токены в репозитории.
- Сохранить миграции, seed и pgTAP-тесты переносимыми в локальный Docker
  контур, не используя этот контур сейчас.

## Не входит в объём

- Автоматическое заполнение удаленной базы seed-данными.
- Автоматическая очистка, `db reset`, применение down-миграции или rollback
  на удаленном проекте.
- Доступ Worker к данным: он появится в следующей серверной задаче.
- Использование прямого PostgreSQL connection string для миграций.

## Архитектура

### Источник истины

`supabase/migrations/20260811000000_task_commander_schema.sql` остаётся
единственным источником структуры. Удаленная база получает только эту
forward-миграцию. История миграций Supabase не редактируется вручную.

### Канал применения

Codex использует Supabase MCP с OAuth-доступом к конкретному проекту. Перед
записью MCP читает историю миграций и схему. Затем применяется отсутствующая
forward-миграция с именем `task_commander_schema`, соответствующая локальному
файлу `20260811000000_task_commander_schema.sql`. Повторный запуск не создаёт
дубликатов: перед записью проверяется имя миграции в удаленной истории.

Direct PostgreSQL connection string не используется в командах, файлах,
документации или журналах. Это исключает попадание пароля в историю оболочки
и отделяет управление схемой от учетных данных приложения.

### Локальное приложение

Когда серверная задача начнёт обращаться к данным, локальный Worker будет
читать `SUPABASE_URL`, `SUPABASE_SERVICE_ROLE_KEY` и
`LOCAL_SUPABASE_ALLOWED_HOSTS` из неотслеживаемого `backend/.dev.vars`.
Шаблон переменных содержит только имена. Браузер не получает service-role
ключ.

## Рабочий процесс

1. Supabase MCP проверяет выбранный проект и текущую историю миграций.
2. MCP применяет только отсутствующую forward-миграцию.
3. MCP запрашивает схему и сверяет таблицы, внешние ключи, индексы, check-
   ограничения, уникальные ключи, RLS и требуемые типы.
4. Изменение в `TASKS.md` допускается только после успешного применения и
   такой проверки.

Seed `supabase/seed.sql` остаётся синтетическим и выполняется только отдельным
явно подтвержденным действием. Любая очистка удаленного проекта также требует
отдельного подтверждения с перечислением затрагиваемых объектов.

## Docker и open-source совместимость

`supabase/config.toml`, миграции, seed и pgTAP-тесты остаются в репозитории.
Документация явно разделяет два режима:

- **remote development** — текущий режим, без Docker и без destructive
  команд;
- **local Docker** — опциональный будущий режим для контрибьюторов, где можно
  запускать `supabase start`, `db reset` и pgTAP-тесты изолированно.

Ни один скрипт текущего стандартного запуска не должен неявно запускать Docker
или очищать удаленную базу.

## Ошибки и безопасность

- При уже примененной миграции действие останавливается как успешно
  синхронизированное; SQL заново не выполняется.
- При ошибке миграции последующие операции не выполняются; состояние и текст
  ошибки берутся из Supabase MCP без секретов.
- При недоступном MCP задача остаётся незавершенной: изменение `TASKS.md` не
  выполняется по наличию SQL-файла.
- Никакие данные и структуры удаленного проекта не удаляются автоматически.

## Проверка готовности

Задача `005` завершена, когда одновременно выполнены условия:

1. Удаленный Supabase содержит миграцию `task_commander_schema` в истории;
   её SQL соответствует локальному файлу `20260811000000_task_commander_schema.sql`.
2. Схема содержит все объекты и инварианты, заданные миграцией.
3. В репозитории отсутствуют секреты и не появилась Docker-зависимость
   обязательного рабочего процесса.
4. `TASKS.md` отмечает задачу как выполненную.
