# Task Commander — дизайн доменных контрактов

## Границы

Задача 003 создаёт единый проверяемый язык данных для webapp, API Worker и Queue consumer. Хранение, экраны и выполнение массовых операций остаются задачами следующих этапов.

Публичный пакет `@task-commander/contracts` содержит только данные, безопасные для браузера: пользователей, права, поля, фильтры, команды изменений, черновики, preview, операции, результаты, отчёты, аудит, health и API-ошибки. Защищённые предыдущие значения, ключи идемпотентности и Queue-модели остаются в `backend`.

## Решения продукта

- Черновики сохраняются 24 часа, имеют ревизию и не попадают в историю завершённых операций.
- Итоговый отчёт содержит все выбранные задачи, включая исключённые и не требующие изменений.
- Исторический отчёт содержит только ID, название, ссылку, названия изменённых полей и безопасный результат; защищённые значения восстановления не экспортируются.
- `Изменения не требуются` и `Частично изменена` являются отдельными результатами задачи.
- Конфликт определяется только по данным, влияющим на подтверждённое изменение, статусу и правам; автоматический rebase и rollback запрещены.

## Техническое устройство

Контракты строятся из строгих Zod-схем. TypeScript-типы выводятся из схем, а не поддерживаются вручную. Валидация выполняется на входе HTTP, перед ответом на внешний контракт, при разборе ответа интеграции и при обработке Queue-сообщения.

Системные даты используют ISO 8601 со смещением часового пояса. ID Битрикс24 передаются decimal-string. Машинные статусы используют стабильные английские коды; русский текст задаётся вне контракта.

API-ошибка имеет код, безопасное русское сообщение, correlation ID формата `TC-<uuid>` и, только для некорректного ввода, структурированные field errors. Токены, HTTP payload интеграции, stack trace и внутренние сообщения не передаются клиенту.

Queue envelope версии 1 содержит только идентификатор операции. Consumer загружает изменения и задачи из защищённой серверной записи, поэтому очередь не несёт восстановительные значения или пользовательские данные.

## Проверка

Unit-тесты проверяют JSON round trip, строгий отказ неизвестных статусов и действий, разделение публичных и защищённых полей, correlation ID и отсутствие утечки секретов. Worker-тесты подтверждают детерминированный `400` для invalid JSON/body и отсутствие R2 side effect для некорректного Queue-сообщения.
