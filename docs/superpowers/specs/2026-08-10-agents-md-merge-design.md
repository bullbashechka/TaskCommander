# Выборочное объединение AGENTS.md

## Цель

Дополнить корневой `AGENTS.md` универсальными правилами инженерной работы из
`di-sukharev/vibe`, сохранив его привязку к Task Commander. Файл должен управлять
поведением агента, а не дублировать продуктовые требования и технические решения.

## Источники истины

- `AGENTS.md` задаёт способ исследования, изменения и проверки репозитория.
- `PRD.md` задаёт требования продукта.
- `design.md` задаёт интерфейс и UX.
- `tasks/` задаёт границы отдельных этапов реализации.
- `docs/decisions/` хранит принятые технические решения.
- Текущие код, контракты, тесты и runtime-результаты имеют приоритет над устаревшим
  описанием; обнаруженный дрейф документации должен быть отмечен или устранён в пределах задачи.

## Структура объединённого файла

### 1. Operating Standard

Добавить краткие правила:

- отвечать на языке пользователя;
- действовать автономно в безопасных границах задачи;
- проверять сомнительные утверждения по репозиторию и runtime-сигналам;
- сохранять несвязанные пользовательские изменения;
- применять самый лёгкий процесс, который доказывает корректность результата.

### 2. Role And Decision Rules

Агент отвечает за архитектуру, качество, безопасность, производительность,
сопровождаемость и документацию затронутых поверхностей. Локальные и обратимые технические
решения принимаются самостоятельно. Согласование требуется для продуктовых развилок,
разрушительных действий, расширения доступа к данным, новых зависимостей и решений,
существенно меняющих стоимость, сроки или эксплуатацию.

### 3. Repository Grounding

Перед нетривиальной работой агент изучает релевантные требования, решения, код, тесты и
соседние модули. Используются Bun, существующие скрипты и уже установленные библиотеки.
Новые runtime- и tooling-зависимости не добавляются без явного разрешения. Общие API-формы
остаются в `packages/contracts`.

### 4. Task Modes

Использовать четыре режима без обязательного объявления пользователю:

- `Review`: чтение и отчёт без изменений;
- `Direct`: очевидная локальная правка без изменения поведения;
- `Investigation`: воспроизведение или трассировка неизвестной причины;
- `Behavior Change`: изменение логики, контрактов, прав, данных или состояния через
  проверяемый acceptance-контракт и тест на наиболее полезной границе.

Для нетривиальной задачи acceptance-контракт содержит от трёх до пяти наблюдаемых критериев,
основной пользовательский сигнал и необходимые вторичные проверки. Для простой локальной
правки отдельный контракт не создаётся.

### 5. Research And Implementation Discipline

Исследование должно находить владеющий проблемой слой:

- UI: маршрут и оболочка → контейнер → hook или handler → контракт API → backend;
- backend: запрос → валидация → идентификация и права → прикладная логика → хранилище или
  внешняя система → ответ;
- асинхронная операция: запуск → очередь → идемпотентность и повтор → побочный эффект →
  статус, аудит и восстановление.

Исправление вносится во владеющий слой. Запрещены локальные компенсации системной ошибки,
преждевременные абстракции и новые архитектурные слои без текущей необходимости. Ясность и
корректные границы важнее минимального числа строк и формального DRY.

### 6. Change-Surface Triggers

- При изменении контрактов проверять producers, consumers, сериализацию и валидацию в
  `webapp`, `backend` и `packages/contracts`.
- При изменении маршрутов проверять прямое открытие, обновление страницы, guards и
  навигационные побочные эффекты.
- При изменении Cloudflare bindings запускать `bun run cf-typegen` и не редактировать
  сгенерированные типы вручную.
- При изменении идентификации или прав проверять Bitrix24-сессию, backend enforcement и все
  видимые состояния отказа.
- При изменении массовых операций проверять лимит 1 000 задач, preflight, идемпотентность,
  повтор, отмену, восстановление, отчётность и аудит в затронутой части сценария.
- При изменении запросов и UI-состояния проверять loading, empty, error, success, disabled,
  stale и recovery states, когда они относятся к поверхности задачи.

### 7. Testing And Validation

Сначала выполняются самые узкие проверки, покрывающие изменённую поверхность. Затем при
необходимости запускаются соответствующие тесты, typecheck, lint и build. Перед запросом
проверки кодового изменения запускается `bun run check`; для изменения только Markdown
достаточно `bun run format:check`. Видимые изменения дополнительно проверяются в runtime.
Изменение общего контракта проверяется с обеих сторон. Косметические детали не фиксируются
тестами конкретных Tailwind-классов или CSS-значений.

Успех нельзя объявлять, если основной пользовательский сигнал остаётся сломанным. Невыполненные
или упавшие проверки указываются явно.

### 8. Git, Safety And Workspace Hygiene

Сохранить существующие правила секретов и добавить:

- не выполнять stage, commit, amend, rebase, reset, stash, push, удаление или переключение
  веток без прямого запроса;
- не закреплять в инструкции `master`, `dev` или другую постоянную ветку: работать в текущей
  ветке и не переключать её без прямого запроса;
- не удалять и не заменять настроенный `origin`;
- не останавливать чужие процессы ради освобождения порта;
- не редактировать generated-файлы вручную;
- держать временные артефакты вне корня репозитория;
- не ослаблять права, валидацию, аудит или защиту данных ради упрощения реализации.

### 9. Existing Project Rules

Сохранить текущие разделы о структуре monorepo, Bun-командах, TypeScript, именовании файлов,
Vitest, стиле коммитов и секретах. Устранить повторы с новыми разделами, не меняя смысл.

### 10. Completion Report

Отчёт должен быть пропорционален задаче и содержать:

- что изменено и зачем;
- первопричину, если она установлена;
- статус основного пользовательского сигнала;
- точные выполненные проверки и их результат;
- состояние документации;
- оставшиеся риски, непроверенные сценарии и миграционные последствия.

Для `Review` и `Direct` отчёт сокращается до релевантных пунктов.

## Исключённые правила исходного файла

Не переносить инструкции, относящиеся к Prisma, PostgreSQL, Docker Compose, Expo, Maestro,
DigitalOcean, mobile E2E, bootstrap шаблона, ветке `master`, удалению `origin`, обязательной
команде `architecture:check` и конкретным каталогам исходного проекта.

## Ограничения реализации

- Изменяется только корневой `AGENTS.md`.
- Вложенные `AGENTS.md` для `webapp` и `backend` не создаются.
- Продуктовые требования не копируются в агентский файл.
- Итоговый файл остаётся компактным: ориентир — не более 180 строк без потери обязательных
  правил.
- Команды должны точно соответствовать существующему `package.json`.

## Проверка результата

1. Все текущие проектные правила сохранены по смыслу.
2. В файле отсутствуют инструкции от чужого стека и шаблона.
3. Нет противоречий между режимами работы, Git-политикой и командами проекта.
4. Все упомянутые пути и команды существуют в Task Commander.
5. `bun run format:check` проходит после изменения файла.
